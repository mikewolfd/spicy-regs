# Comments mirror capacity admission

The manual comments publication route uses `scripts/publish_comments_mirror_guarded.py` around the existing publisher. Dispatch the reviewed workflow ref with `comments_only=true` when the task requires only comments. The wrapper verifies the checked-out commit against the workflow's `GITHUB_SHA`, requires `comments-catalog-write`, and preserves the existing 3GB/one-thread query settings, snapshot/schema checks, prior-ID coverage, shrink guards, generation selection and complete public-byte readback.

Before any subject or receipt payload export, a bounded metadata phase records the selected native snapshot and the sizes, ETags and optional version IDs of every live native data/delete object. It uses manifest metadata and object HEAD requests, plus a HEAD of the prior monolith. It refuses a moving snapshot, foreign bucket, missing size or excessive metadata inventory. This is capacity evidence; the maintained publisher still validates initialization and the declared native schema.

Let `B` be the larger of the total native object bytes and the prior monolith bytes. The owned-output cap is `5 × B + 8GiB`: four copy equivalents with 25% growth headroom, plus spill and control space. Available disk must cover that entire cap plus an 8GiB free-space floor before export. The publisher rechecks the admitted snapshot, predecessor and free disk before starting. Standard Ubuntu is acceptable when its actual free disk passes; this route neither buys a runner nor removes unrelated software to create room.

The complete active run has a 150-minute deadline within the existing 180-minute job. Metadata admission runs first under a 15-minute/1GiB-RSS/64MiB-output bound. Publication uses the remaining active time, an 8GiB whole-process-tree RSS limit, the computed output cap and the same 8GiB free-space floor. The existing process-birth watchdog closes the observed child tree on refusal, timeout or interruption and retains both phases' logs, resource measurements and closure records. Sampling can overshoot; these are measured stop conditions rather than an operating-system sandbox. A workload exceeding them requires review of its retained measurements.

These choices use the successful [hosted mirror run 42872563797](https://github.com/mikewolfd/spicy-regs/actions/runs/42872563797): 69m14s, 4,240,752KiB maximum RSS, 92,592,128,000 bytes initially free, with the same query and bounded-row-group settings. Its `comments-publication-42872563797` artifact has SHA-256 `bf2a875f2d09d92a66205180e81bf6e466da462195fcd67a58bfba7bc1e78ff2`. Cumulative filesystem I/O in that report is not a peak-disk measurement; current admission measures its own input sizes and free space.

The `comments-publication-<run>` artifact retains placement, admission, build/publication receipts and both phases' execution/closure logs on success or failure. Use a fresh output directory for a new run. The guard adds no rollback: fixed public paths can be partly updated if the process stops before generation selection or final receipt upload. A selected generation may already have committed when a later check fails. Inspect the actual current pointer, receipt and object versions, then use the maintained retry/readback route; never infer an uncommitted publication from a failed job alone.
