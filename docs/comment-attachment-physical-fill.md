# Fill attachment stages by native data file

Use the manual `fill-comment-attachment-groups.yml` workflow after the complete source stage has passed its own checks and the selected native schema has been migrated under the existing maintenance guard. Run the reviewed exact `runtime_ref` only after its required CI passes. This workflow does not migrate the schema or select a publication. It calls the maintained physical-group planner, stage checker and attachment-only prepare/write/undo functions.

The workflow holds `comments-catalog-write` across planning and its sequential matrix. Every writing job saves and suspends the exact prior maintenance settings for both selected native tables, verifies the guard immediately before the write, and restores both tables in the supervisor's cleanup. A second `always()` step repeats restoration and journal retention if the supervisor itself was interrupted. An in-flight external maintenance operation makes the guard refuse; disabling a schedule does not cancel that operation.

## Inputs and admission

All operations take an exact repository commit and a JSON `config`. A file descriptor is `{"key":"staging/...","sha256":"<64 hex>","bytes":123}`. `bytes` is optional for small caller-pinned controls; the checked receipt supplies the actual stage size. No source original is downloaded by this workflow.

1. **Plan:** supply `{"reads":<aggregate reads descriptor>,"staging":<aggregate staging.json descriptor>}`. The hosted planner downloads the aggregate once, freezes identity membership against one native snapshot, and stages every group with all source copies. It uploads and reads back each immutable group before removing that temporary local group. `result.json` supplies the new `plan` descriptor and original physical-plan controls. Retain these records and inspect the exclusion outcomes.
2. **Pilot:** supply `{"plan":<plan descriptor>,"group":0}` with an explicitly reviewed representative group ID. The job fetches only that group's stage. A successful writing pilot produces `published-result.json`, the descriptor of its immutable result. The result includes the changed-row total and recovery receipt hash. A zero-change pilot cannot authorize the remaining fill.
3. **Fill:** supply `{"plan":<same descriptor>,"pilot":<successful pilot result descriptor>}`. The matrix selects remaining groups and runs one at a time; an error stops subsequent jobs. Each writer also requires the pilot's exact prepare journal after merging current shared history, so a missing, unresolved or undone pilot cannot authorize the fill through an old immutable success receipt. An optional `"groups":[2,3]` restricts a dispatch to reviewed remaining groups, excluding the pilot. This also permits a campaign larger than the matrix limit to proceed in explicit sets. Already verified successful groups should be omitted from later dispatches.

The planner uses the script's fixed bounds of one million candidate identities and 512MiB source-value bytes per group. If these split an original physical file, planning refuses and retains the incomplete plan for review; it does not rewrite that file through several groups. Original file names guide locality only. Each write prepares against the current catalog snapshot and retains the maintained same-version, additive-value, all-copy agreement and native receipt checks.

The process-tree watchdog caps observed RSS at 8GiB, owned inputs/output/preimages/spill at 6GiB, and active execution at 300 minutes, with a 4GiB free-disk floor. The workflow leaves a further cleanup/artifact interval. Planning admits the pinned aggregate plus 2GiB working reserve before download. A fill admits its group download plus working reserve, then uses actual prepared native file sizes to reserve at least 1GiB for preimages, twice touched compressed bytes plus source-value bytes when larger, and 1GiB spill. DuckDB grouping uses its maintained 256MB query target; writer queries use 2GB and a 1GB spill ceiling.

These admission estimates are deliberately explicit, not a measured guarantee that all groups fit. Restored receipt values can exceed compressed native bytes. The whole-process sampler checks actual growth and terminates the owned child tree on a limit; a preimage and pending journal already written remain recovery evidence. It can overshoot between samples. A stage too large for aggregate admission needs a separately reviewed runner/budget; do not lower the free-space floor or run a full native workload on the workstation. Measure the hosted pilot before admitting a larger campaign.

## Recovery and undo

Every job retains `comment-attachment-fill-<group>` with its complete writer journal, prepare inputs, preimages, postimage digests, group stage, maintenance observations and `recovery.json`. Its hashes bind the exact runtime, plan and group. The aggregate itself is excluded; subsequent jobs use per-group stages. Journals also use the existing shared prefix beside the aggregate. Downloaded and retained histories must be prefix-compatible, including a fresh compatibility check before cleanup pushes anything. A pending journal without the original prepare and verified preimage blocks another prepare; a committed verification failure blocks later groups.

A current-attempt success marker binds the worker's unchanged result. After successful restoration and journal retention, cleanup publishes a separate completion with the current recovery hash. Repeated cleanup may capture newer maintenance observations; it updates the completion descriptor to match the final artifact. A cleanup failure removes the stale published descriptor and retains evidence for retry. A rejected prior artifact has no authority to restore settings or push journals in the current attempt.

For **resume**, set `resume_run_id` to the earlier run and use `{"plan":<same descriptor>,"group":0,"recovery_sha256":"<hash of recovery.json>"}`. The restored path remains `/tmp/comment-attachment-fill`, preserving journaled preimage paths. The executor verifies every retained member before reuse, then calls the existing writer's pending-commit recovery and verified-batch skipping. It does not automatically clear a failed check. If the process stopped before preparing, resume can prepare only after the pending/committed failure checks pass. A writing pilot resumed after its commit retains its original pilot identity and total verified changed rows.

For a **committed failure**, inspect the retained journal and live snapshot, then use **undo** with the same recovery pins plus `"undo_batch":"<journal batch>","expected_snapshot":123`. Undo uses the existing preimage/postimage comparison and expected-snapshot guard; it refuses subsequent edits. The updated journal is retained and synchronized. An undone prepare cannot resume its earlier verified batches; use a fresh explicit pilot/prepare after reviewing the undo. Repeat maintenance restoration if its evidence records a failed restore. Never invent an empty journal or use a fresh prepare to bypass a pending or committed failure.

Actions artifacts have finite retention and the repository's artifact access rules. Preimages contain the original native rows required for undo, including existing comment fields. Retain required recovery artifacts before expiry. An abrupt loss of the entire VM can prevent any `finally` or `always()` cleanup; a cancelled/lost writer must be reconciled from its run, live snapshots and retained evidence before another dispatch. An absent success result is not proof that nothing committed.
