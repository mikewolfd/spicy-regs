# MCP blind persona test, 2026-09-28

Decision: what stops a person from answering a real question through the fork MCP, and is the answer they reach right?

Method: the workspace `mcp-chaos-test` skill. Five blind personas each asked one question from their own role. Each used only the MCP tools, within a 40-call budget, against the deployed Worker `11f280ae`. That Worker was built from spicy-regs `6d002cc` and ran container version 16 as a single instance. The sessions ran in Claude Code. Beginners ran on the smaller models. Before the run, the 2026-09-27 regression cases were replayed against the same Worker, and all 42 stated expectations passed. An independent auditor then re-derived each answered question twice: once from the published Parquet, reading it directly, and once from the publisher's own records. The evidence is kept locally, outside Git, under `~/Work/corpora/mcp-chaos-2026-09-28/`: the target record, persona reports, audits and replay receipts.

| --- | --- | --- |
| Political-science student: House members who broke with their party most often, 118th Congress | No answer. Every result was unreadable, and the one analytic query hit two HTTP 429s | — |
| Advocacy analyst: EPA PFAS docket comments, organization share, form letters | No answer. Every result was unreadable | — |

## Findings

1. **Replies too large to read (server; repaired below).** Each reply carried metadata for every table:
   - `list_sources` returned 163,702 characters and `query_sql` about 54,400 characters, even for `SELECT 1`.
   - The client wrote each oversized reply to a single-line file that its reader could not page through.
   - Two personas never read a row. The personas who did get answers found tables only through fragments of that metadata.
2. **Public r2.dev bucket throttling (deployment; mitigated in the server, domain pending).** The server reads Parquet through the public r2.dev endpoint.
   - That endpoint answered HTTP 429 to a `member_votes` scan and to a `describe_table` HEAD request while the five sessions ran.
   - Cloudflare documents r2.dev as rate-limited and not intended for production traffic.
3. **A parallel call returned another table's columns (a client defect).**
   - One of two concurrent `query_sql` calls came back with only `fec_relationships`' column set.
   - A repeat run on its own was correct.
   - The client may have read the wrong spill file; that is not yet separated from a server defect.
4. **Descriptions that let a careful reader reach a wrong answer (data and metadata; repaired below).**
   - `comment_periods`:
     - Its coverage and summary say it covers all dated inputs and merges docket halves with proceeding halves. The builder does neither.
     - Feed dockets chain unrelated notices into one period.
   - `fcc_filings`: the "window" gives no dates.
   - `fcc_proceedings.date_closed`: two open sentinels exist, and one is documented.
   - `court_dockets`: its label oversells a district-court Administrative Procedure Act selection.
   - `fec_source_records`:
     - It does not say that `committee_id` is the filing committee.
     - It does not say that `fec_intercommittee` is almost entirely memo lines for individual joint-fundraising shares.
     - It carries no cycle column.
     - It does not say which contribution files are expanded.
   - `lobbying_filings`: its coverage note states 287,246 rows, while the live generation holds 1,411,548.
5. **Refusals held.** A local file read, an INSERT and a stacked CREATE were each refused with a clear message.

## Repair: a reply carries what its caller asked about

- `list_sources` now returns each table's name, label and coverage kind (`true_range`, `window`, `sampled` or `derived`). Each relationship family's views are listed once, under their shared summary.
- Publication pins, ledger audits and view dependencies now come only from `describe_table`.
- `query_sql` returns the pin of each table its statement names, read from DuckDB's unbound parse tree.
- `describe_table` returns one column list. The duplicated `declared_columns` list is gone, along with DESCRIBE's null, key and default fields, which carry no information for a Parquet view.
- A misspelled table name is answered with the closest names.

## Further repairs in the same change

- **Connection lifecycle.**
  - At the 300 s TTL the server re-reads the published pointers and rebuilds only when they moved. An idle refresh fell from 464 requests to 3 in a measured single-client build.
  - A failed refresh keeps serving the current connection, and other callers are served while a rebuild runs; only a cold start fails.
  - A legacy table is skipped only on a 404, so a throttled read refuses the build instead of silently dropping the table.
  - An interactive retry policy (4 retries, at most about 7 s of backoff per request) is set before the configuration lock.
  - DuckDB 1.5.5 does retry a 429: first immediately, then with backoff. It ignores `Retry-After`.
- **Concurrency.**
  - The server moved to `mcp` 2.2. Its `MCPServer` runs each tool on a worker thread, where 1.x ran every tool on the event loop, one call at a time.
  - `SPICY_REGS_TOOL_CONCURRENCY` caps concurrent tools (default 2, to stay near one scan's measured request rate on r2.dev).
  - Every failure is raised as a tool error, so its text still reaches the caller. Tool input and output schemas are unchanged.
- **The client defect.**
  - Claude Code named the file for an oversized reply by millisecond. Two sibling subagents whose replies finished in the same millisecond were given one path, and the second reply was lost.
  - A server that no longer bloats replies rarely triggers it. `query_sql` now echoes the statement it answers, so a reader can see when a reply is not its own.
  - The client bug was reported upstream.
- **Live facts.** `describe_table` and each table a query names report the pinned `rows`, the snapshot's `run_id` and `asserted_at`, and the coverage kind. `rows` was checked against `COUNT(*)` over the file.
- **Descriptions.**
  - Meaning notes sit on the columns where a wrong filter or sum is written:
    - an FEC row's `committee_id` is the filer;
    - memo lines are not summed;
    - individual contributions are mostly absent;
    - FCC proceedings are open when `date_closed` is null or later than today;
    - `court_dockets` holds APA suits, mostly in district courts, and points to `court_opinion_clusters`.
  - A new `fec_collection_cycles` view states the cycle of each FEC bulk collection.
  - Coverage prose no longer states row counts, snapshot ids, pins or publication status. A dictionary lint refuses them, because the server states them live.
  - Two notes that looked like lost data (`gao_reports`, and `lobbying_filings` before 2010) had been measured against upstream's bucket, not the fork's; nothing had been dropped.
- **`comment_periods`.**
  - Rebuilt as one period per notice. Periods merge only on explicit links: a notice's Register record and its Regulations.gov copies by document number, and an extension or reopening that cites the notice or shares its only open RIN.
  - Every notice that states a close date is kept, with `anchor_kind` (docket, proceeding, none). The rulespec export is the anchored rows.
  - Close dates on or after 2050 are ignored as placeholders.
  - On the published inputs, 347 of the 351 Federal Register notices closing 2026-09-28 to 10-11 now sit in a period closing in that window, up from 196.
  - The table grows from 281,635 to 640,117 periods, and every period id changes.
