# Blind MCP research round 4, October 3, 2026

Decision: run the loop again on the round-3 release the same day, with ten expert personas aimed at the repaired areas and at families round 3 did not touch, audit every answer by another route, and let a no-tools reviewer reshape the fixes before anything is built. Round 3's class of defect was decaying numbers in prose; round 4's class is semantic promises nobody measured. The repair for that class is a measured claim or a stated limit, never a longer sentence.

The decision rule for every finding stayed the same: reproduce it independently (fresh SQL over the pinned Parquet, then the publisher's record), locate the owning layer in the code and the data, state a publisher limit instead of repairing it, require RED tests before GREEN, and ship data repairs through the transform that owns them rather than a caveat.

## Research results

Ten personas, all at the same model tier, drafted after surveying every live table. Every persona answered; none hit a tool error that was not its own SQL; none timed out. Ten auditors re-derived every headline over the same publication pins and spot-checked identifiers at the publisher. Every answer was correct within its scope, every one with caveats the persona had not stated, and no confident wrong headline was the service's doing. ## Root causes and repairs

Four read-only scouts traced the issues by layer; a no-tools reviewer then challenged every proposed fix. Declared metadata held the most root causes (12), then the publisher as limits to state (8), acquisition (6), the server (5), transforms (4), publication (2), deployment and FEC policy (1 each).

The reviewer blocked two proposals and changed most of the rest. A `petition_receipt` proposal form would have promoted a title pattern to a classification and relabelled 164 non-pesticide proposals; the dictionary states the limit instead. A Worker replay of the first request after a rollout was refused because the server is stateless and the documented reset is right. The stage rule is fixed in spicy-docs by deriving the chamber from the bill type and letting each calendar matcher name the chamber it means, with no new required parameter; a reported bill placed on its own calendar classifies nothing, and whether calendar placement deserves its own stage is an owner question the handoff states.

## Verification boundaries

The merged consumer passed its full gate: dictionary generation with no diff, lint, type check, dictionary check over 155 tables, strict documentation build, Worker tests and dry run, and 4,844 tests. The built image passed the release binding: 72 FEC views compatible with the prior release's output membership, SQL, dependencies, population, as-of and evidence generations unchanged, only descriptions and acceptance receipts moved; the wrong-image, wrong-policy, missing-parent, advanced-parent, missing-receipt and old-query-generation controls each disable all 72 views. The local container then replayed the 74 retained controls, the 17 round-3 positive cases, the 25 dictionary and 10 server cases from this round, and the 9 round-3 RED cases: every control and new case passed; the six round-3 relationship-view cases stayed green; the three round-3 data-pending cases stayed red; the two CFR query cases stay red until the daily CFR run republishes. The deployed service then replayed the same 138 cases with the same result, and its `list_sources` names the bound receipt with 72 compatible views and the two comment exports' row counts from their receipt. Three deployed calls exceeded ten seconds: the first `list_sources` after the rollout (75 s, the cold start), the one-row qualified FEC query (29.5 s) and a court-cluster window count (19.8 s).

Two checks found defects in the checks themselves. The replay tool's needle search ran over the whole structured reply, which echoes the SQL statement, so a query that named its expected verdict in its own text could never fail; the search now excludes the echoed statement, and the two CFR cases that had passed by echo now fail honestly until their data lands. The reply-boundary check in the release runner compared the default describe reply against the full stored record; that default is now a projection by design, so the check compares the projected fields and reads the full record through the detail flag.

Publisher spot-checks support selected FEC committee totals and schedule counts (OpenFEC), FCC filing counts (ECFS), Clerk roll-call XML, GovInfo bill status, reports and PLAW packages, the Federal Register API's facets, CourtListener's search API, USAspending recipient profiles and LDA filing pages. They do not certify whole populations. Regulations.gov's demonstration key was exhausted for every auditor who tried it; CourtListener's HTML answers a challenge and its clusters API a 401; the Law Revision Counsel's site answered HTTP 200 with a maintenance page all day, which the laws rollup now journals as a refused read.

## Remaining limits and owner handoff

Stated limits: ECFS re-dockets filings out of inbox placeholders and the window re-reads only seven days; CourtListener's citator links late and holds no 143 to 144 S. Ct. volume; FDA and EPA state no organization; the "proposal" of a pesticide tolerance is usually the petition-receipt notice; LDA carries no UEI and scopes client ids per registrant; GovInfo lags new laws and has no part-level granule for 50 CFR 622; a missing Clerk roll answers HTTP 200 with a stub and the EVS index pages are gone; the comment body is an HTML fragment by contract.

Owner decisions this round states: scope the FEC consumer identity to what each view depends on, so wording edits stop moving sealed identities; keep vocabularies (document kinds, CFR part parsing, chamber words, title types, party labels) in one registry; decide the petition-receipt form together with whether Notice-typed withdrawals become lifecycle events; a calendared stage or flag for bills placed on their own chamber's calendar; FEC policy version 4 (layout-specific refusal reasons, a direction warning backed by a retained transaction-type definition, a `Total_Receipt` view, summary-row selection); how much of the House roll-call archive to re-read for party totals; a cluster-grouping table for Supreme Court decisions.

Bills-lane handoff: spicy-docs branch `chaos/2026-10-03-bills-lane-r4` (tip `e4810ea`, seven commits on the round-3 branch, package 0.54.0) carries the House roll-call lister that no longer needs the Clerk's retired index pages (it recognizes the Clerk's 65-byte stub by content and probes forward from the last held roll; live, the 116th second session lists 253 rolls in seven requests and the 119th first session 362), the chamber-aware stage rule (659 bills move in the 119th, 3,649 in the 113th to 118th and 2,505 in the 108th to 112th; 40 of 40 sampled movers carry their own chamber's reported or calendar printing at GovInfo and no other-chamber printing), the short-title rule that skips portion titles (42 bills change), a `bill_committee_activities` contract table (32,102 rows for the 119th), and `party_totals_json` on roll calls. Nothing there is merged, released or vendored. At adoption spicy-regs owes the consumer change that passes the bill type and source system to the stage re-derivation, the family, dictionary and ledger entries for the new table, the lister's starting roll, the wheel pin, the deletion of the four expiring interim notes, and the runs: the votes chain, the 119th bill-family re-read with dispatches for earlier Congresses, the laws re-read under the round-3 text reader, and a print-citations rerun. The handoff with measurements is `round4/implementation-spicydocs.md`.
